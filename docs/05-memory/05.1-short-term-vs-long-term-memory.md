# 5.1 Short-term vs long-term memory

> **Difficulty:** 🟢 Beginner · **Reading time:** ~8 min · **Prerequisites:** [1.4 How LLMs work](../01-foundations/01.4-how-llms-work.md), [1.5 Anatomy of an agent](../01-foundations/01.5-anatomy-of-an-agent.md)

**In one sentence:** Short-term memory is whatever is in the context window for this call; long-term memory is anything your code stores outside the model and puts back into the context when it's relevant, and every memory feature you will meet is one of those two, or a way of moving information between them.

## 🤔 Why does this matter?

Two complaints come up with almost every [agent](../../GLOSSARY.md#agent):

- *"I told it yesterday that I'm vegetarian, and today it suggested a steakhouse."* The agent has no memory across conversations.
- *"Halfway through a long task it forgot what I asked for at the start."* The conversation grew too long, and early details were cut or got lost.

Both are memory problems, but they are different problems with different fixes. This page separates them, so the rest of the chapter has clear names to work with.

## 🧠 The idea, in plain words

Think of a chef in a busy kitchen.

- The **counter** in front of them is small. Whatever is on it right now (today's order tickets, the ingredients for this dish) is all they can work with. That's **short-term memory**: the model's [context window](../../GLOSSARY.md#context-window).
- The **pantry and recipe binder** at the back hold far more, and they last for years. But the chef only benefits from them when someone fetches the right jar or page and puts it on the counter. That's **long-term memory**: databases, files or vector stores that your code manages.

Two facts from [1.4](../01-foundations/01.4-how-llms-work.md) make this concrete:

1. The model is [stateless](../../GLOSSARY.md#stateless). It keeps nothing between calls. It "remembers" only what you send in the current request.
2. The context window is finite, and filling it is not free: you pay for every [token](../../GLOSSARY.md#token), long requests are slower, and models get worse at using information as the context grows. Anthropic's engineering team calls this decline *context rot*.

So:

| | Short-term memory | Long-term memory |
| --- | --- | --- |
| Where it lives | In the request: system prompt + messages + tool results | Outside the model: a database, files, a vector store |
| How long it lasts | One call (you resend it each time) | Across conversations, until you delete it |
| Size | Limited by the context window | As big as your storage |
| Who manages it | Your loop appends messages | Your code decides what to write, and what to recall |
| Typical failure | Overflows, or gets noisy and distracting | Recalls the wrong thing, or stale and private things |
| Covered in | [5.2](./05.2-summarisation-and-context-compaction.md) | [5.3](./05.3-vector-memory.md), [5.4](./05.4-episodic-semantic-and-procedural-memory.md), [5.5](./05.5-memory-design-trade-offs.md) |

There is a third, hidden kind: what the model learned in training, stored in its weights. You can't edit it per user, so for agents it behaves like fixed background knowledge.

## 🔍 How it works, step by step

**Short-term memory, during one run:**

1. Your loop starts with the [system prompt](../../GLOSSARY.md#system-prompt) and the user's message.
2. Each step appends the model's reply, any [tool](../../GLOSSARY.md#tool) calls and their results ([2.1](../02-the-agent-loop/02.1-the-observe-think-act-loop.md)). The context grows every step.
3. When it gets too big or too noisy, you shrink it: drop old turns, summarise them, or clear old tool results. That's [5.2](./05.2-summarisation-and-context-compaction.md).

**Long-term memory, across runs:**

1. **Write.** Decide what is worth keeping (a preference, a decision, a lesson learned) and save it, either at the end of a turn or when the model calls a "remember" tool.
2. **Store.** Anything from a JSON file to a database or a vector index. The format depends on how you will look it up.
3. **Recall.** Before (or during) a run, fetch what's relevant: everything for a small profile, or a similarity search for a large store ([5.3](./05.3-vector-memory.md)).
4. **Inject.** Put the recalled items into the context, usually the system prompt or a tool result. Now they are short-term memory for this call.

The [short-term](../../GLOSSARY.md#short-term-memory)/[long-term](../../GLOSSARY.md#long-term-memory) split is the most useful first cut. [5.4](./05.4-episodic-semantic-and-procedural-memory.md) splits long-term memory further, by *what kind* of thing is remembered: facts, experiences or skills.

## 💡 Worked example

From [`examples/05-vector-memory`](../../examples/05-vector-memory/README.md), run offline. Two separate conversations with the same travel assistant:

```text
SESSION 1: Please remember: my daughter Mia is allergic to peanuts. Also, I always prefer window seats on flights.
  answer: Got it. I'll remember both.
  remember({'fact': "The user's daughter Mia is allergic to peanuts."}) -> 'Saved memory #2.'
  remember({'fact': 'The user prefers window seats on flights.'}) -> 'Saved memory #3.'
  saved 3 memories to agentic-ai-notes-vector-memory.json

SESSION 2 (new conversation, memory loaded from disk): Find me a flight to Oslo next week, and suggest a snack for Mia for the trip.
  answer: I'll look for flights to Oslo with a window seat, and pack a peanut-free snack for Mia.
  recall({'query': 'flight seat preference'}) -> '[0.58] The user prefers window seats on flights.'
  recall({'query': 'Mia snack'}) -> "[0.35] The user's daughter Mia is allergic to peanuts."
```

Follow the information:

| Moment | Short-term memory (context) | Long-term memory (file on disk) |
| --- | --- | --- |
| Session 1, user speaks | The user's message, with both facts | 1 item (from the signup form) |
| Session 1, after `remember` | Message + two tool results | 3 items, written by the tool |
| Session 2 starts | **Only** the new question: one message | Still 3 items |
| Session 2, after `recall` | Question + the two recalled facts | 3 items, unchanged |

Session 2's context began empty of anything about Mia. The facts only reached the model because the agent *recalled* them into the context.

## 💻 Code

The simplest possible long-term memory: a JSON file of facts, loaded into the system prompt at the start of every conversation. Plain Python plus the shared wrapper from [0.3](../00-start-here/00.3-setup.md):

```python
import json
from pathlib import Path

from common import get_llm, user

MEMORY_FILE = Path("user_facts.json")


def load_facts() -> list[str]:
    return json.loads(MEMORY_FILE.read_text()) if MEMORY_FILE.exists() else []


def save_fact(fact: str) -> None:                       # WRITE: called when the user says "remember ..."
    MEMORY_FILE.write_text(json.dumps(load_facts() + [fact]))


def chat(question: str) -> str:
    facts = load_facts()                                 # RECALL: here, simply everything
    system = "You are a helpful travel assistant."
    if facts:                                            # INJECT: long-term -> short-term
        system += "\n\nWhat you know about the user:\n" + "\n".join(f"- {f}" for f in facts)
    llm = get_llm(mock_responses=["(scripted reply)"])
    return llm.chat([user(question)], system=system).text  # a brand-new conversation each time


save_fact("Vegetarian.")
print(chat("Suggest a restaurant for tonight."))         # the model sees "Vegetarian." in its system prompt
```

This "load everything" approach is fine for a handful of facts. When you have hundreds, you need to recall selectively ([5.3](./05.3-vector-memory.md)), and decide what deserves to be written at all ([5.5](./05.5-memory-design-trade-offs.md)). The full agents are in [`examples/05-vector-memory`](../../examples/05-vector-memory/README.md) and [`examples/05-memory-types`](../../examples/05-memory-types/README.md).

## 🚨 Common mistakes & gotchas

- **Calling chat history "memory" and stopping there.** Resending the conversation is short-term memory. It disappears when the conversation ends, and it can't grow forever.
- **Counting on a big context window.** Even a window of a million tokens costs money to fill, slows responses and suffers from context rot. Bigger windows delay the problem; they don't remove it.
- **Mistaking server-side conversation state for long-term memory.** Some APIs can store a conversation for you (for example OpenAI's conversation state options in the Responses API). That saves resending, but it is still one conversation's short-term history, not curated facts about the user.
- **Storing everything "just in case".** Recalling irrelevant memories distracts the model just like irrelevant history does. Write deliberately.
- **Forgetting that long-term memory is data about people.** It needs the same care as any user data: consent, access control and deletion ([5.5](./05.5-memory-design-trade-offs.md)).

## ✅ Key takeaways

- Short-term memory = the context window for this call. Long-term memory = what your code stores outside the model.
- The model only knows what is in the current request; long-term memory helps only once it is recalled into the context.
- Short-term memory's problem is space and noise (5.2). Long-term memory's problems are what to write and what to recall (5.3 to 5.5).
- Every long-term memory system has the same four steps: write, store, recall, inject.
