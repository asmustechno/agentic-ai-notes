# 11.1 Framework landscape

## 🤔 Why does this matter?

Priya's team wants to ship a support agent. In one afternoon of searching she finds LangGraph, CrewAI, AutoGen, Microsoft Agent Framework, the OpenAI Agents SDK, the Claude Agent SDK, LlamaIndex and Pydantic AI. Each home page promises "production-ready agents". Each uses different words: graphs, crews, runners, harnesses, workflows.

Without a map, teams pick the framework they heard of first, then fight it for months. With a map, you can ask a better question: *which parts of the agent do I want someone else to own?*

This chapter is that map. Every framework page rebuilds **the same agent** from [1.5](../01-foundations/01.5-anatomy-of-an-agent.md), so you compare like with like.

## 🧠 The idea, in plain words

An [agent framework](../../GLOSSARY.md#agent-framework) is a library that gives you ready-made pieces for building an [agent](../../GLOSSARY.md#agent): the [agent loop](../../GLOSSARY.md#agent-loop), [tool](../../GLOSSARY.md#tool) schemas built from your functions, memory, tracing, and ways for several agents to work together.

Think of building a kitchen. You can buy loose parts and fit them yourself (the provider SDK plus your own loop). You can buy flat-pack units that click together (an agent SDK). You can hire a designer who plans how the whole room flows (an orchestration framework). Or you can rent a fully equipped kitchen and just cook (a harness). None of these is "best". It depends how much you want to control, and how much you want to own.

Here is the same agent's five parts under each framework's names:

| Part | LangGraph | CrewAI | Agent Framework | OpenAI Agents SDK | Claude Agent SDK | LlamaIndex | Pydantic AI |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ① Model | chat model (`init_chat_model`) | `LLM` | chat client | `model=` | `model=` (Claude only) | `llm=` | `model=` string |
| ② Instructions | a `SystemMessage` in your node | role, goal, backstory + task | `instructions=` | `instructions=` | `system_prompt=` | `system_prompt=` | `instructions=` |
| ③ Tools | `@tool` | `@tool("name")` | plain functions | `@tool` | `@tool` + in-process MCP server | plain functions | `@agent.tool_plain` |
| ④ Memory | graph state + checkpointer | crew memory | `AgentSession` | sessions | sessions | memory / `Context` | message history |
| ⑤ Loop | edges you draw | crew process | function invocation layer | `Runner` | Claude Code's loop | `FunctionAgent` workflow | `agent.run` |

## 🔍 How it works, step by step

Whatever the framework, a run goes through the same steps. The framework just owns different steps.

1. **You describe tools.** You write normal functions. The framework reads names, type hints and docstrings and builds the [JSON Schema](../../GLOSSARY.md#json-schema) the model needs ([3.2](../03-tools-and-function-calling/03.2-json-schema-for-tools.md)).
2. **You configure the agent.** Model, instructions and tools go into one object: `Agent`, `Crew`, `StateGraph` or `ClaudeAgentOptions`.
3. **The framework runs the loop.** It calls the model, runs the requested tools, sends results back and repeats, with a limit (`max_turns`, `max_iter`, `recursion_limit`, `UsageLimits`).
4. **It records what happened.** Most frameworks emit events or [traces](../../GLOSSARY.md#trace) you can print, test or send to a tracing tool ([14.1](../14-observability-and-debugging/14.1-tracing-agent-runs.md)).
5. **It returns a result.** Usually the final text, sometimes a typed object (Pydantic AI, OpenAI Agents SDK), plus the message history.

### The comparison table

Checked against each project's official docs, PyPI page and repository in November 2026.

| Framework | Maintainer | Core abstraction | Multi-agent support | Model providers | Licence | Best for |
| --- | --- | --- | --- | --- | --- | --- |
| [LangGraph](./11.2-langgraph.md) | LangChain | `StateGraph`: nodes, edges and shared state | Yes: any topology you can draw as a graph | Any chat model with a LangChain integration (Anthropic, OpenAI and many more); nodes can be plain Python | MIT | Long-running, stateful agents that need explicit control flow, persistence and human-in-the-loop |
| [CrewAI](./11.3-crewai.md) | CrewAI | `Agent` (role, goal, backstory), `Task`, `Crew`; `Flow` for event-driven pipelines | Yes: crews run tasks in a sequential or hierarchical (manager) process | Native: OpenAI, Anthropic, Gemini, Azure, Bedrock and others; the rest through LiteLLM | MIT | Role-based teams of agents, quick to prototype |
| [AutoGen](./11.4-microsoft-autogen-and-agent-framework.md) | Microsoft (**archived**) | `AssistantAgent` and teams in AgentChat, on an event-driven core | Yes: teams and group chats | OpenAI, Azure, Anthropic, Gemini, Ollama and others through `autogen-ext` | MIT (code), CC BY 4.0 (docs) | Reading and migrating existing code only |
| [Microsoft Agent Framework](./11.4-microsoft-autogen-and-agent-framework.md) | Microsoft | `Agent` (chat client, instructions, tools) and graph-based `Workflow` | Yes: workflow orchestrations (sequential, concurrent, handoff, group chat, Magentic) | Microsoft Foundry, Azure OpenAI, OpenAI, Anthropic, Ollama and more | MIT | Python or .NET teams, especially on Azure; successor to AutoGen and Semantic Kernel |
| [OpenAI Agents SDK](./11.5-openai-agents-sdk.md) | OpenAI | `Agent` run by `Runner` | Yes: handoffs and agents as tools | OpenAI by default; OpenAI-compatible endpoints; LiteLLM and Any-LLM adapters (beta) | MIT | A small API with built-in tracing and guardrails, especially on OpenAI models |
| [Claude Agent SDK](./11.6-claude-agent-sdk.md) | Anthropic | `query()` and `ClaudeSDKClient` driving the Claude Code harness | Yes: subagents | Claude models only: Claude API, Amazon Bedrock, Google Cloud, Microsoft Foundry | MIT (repository); use is governed by Anthropic's Commercial Terms | Agents that read and edit files, run commands and need permissions and hooks built in |
| [LlamaIndex](./11.7-llamaindex-agents.md) | LlamaIndex | `FunctionAgent`, `ReActAgent`, `CodeActAgent` on event-driven Workflows | Yes: `AgentWorkflow` handoffs, orchestrator agents | Many, through `llama-index-llms-*` packages | MIT | Agents over your own documents and data ([RAG](../../GLOSSARY.md#retrieval-augmented-generation-rag)) |
| [Pydantic AI](./11.8-pydantic-ai.md) | Pydantic | `Agent` with typed dependencies and typed output | Yes: agent delegation, programmatic hand-off, graphs | OpenAI, Anthropic, Google, Bedrock, Groq, Mistral, Ollama and many more | MIT | Type-safe Python apps where validated, structured output matters |
| [No framework](./11.9-the-no-framework-approach.md) | You | A `for` loop over the provider SDK | Whatever you write | Whichever SDKs you call | Yours | Simple agents, learning, and full control |

## 💡 Worked example

All the examples in this chapter solve one task from [1.5](../01-foundations/01.5-anatomy-of-an-agent.md): *"Is it warmer in Paris or Rome right now, and by how much?"*, with a fake `get_weather` (Paris 14 °C, Rome 19 °C, London 11 °C) and a safe `calculator`. Each one runs offline with that framework's own [fake model](../../GLOSSARY.md#fake-model) where one exists.

Every example that runs offline makes the same three model calls and the same three tool calls. Here is the trace from [`examples/11-pydantic-ai`](../../examples/11-pydantic-ai/README.md):

```text
tool call:   get_weather({"city":"Paris"})
tool call:   get_weather({"city":"Rome"})
tool result: {"city": "Paris", "temp_c": 14}
tool result: {"city": "Rome", "temp_c": 19}
tool call:   calculator({"expression":"19 - 14"})
tool result: 5

Answer: Rome is warmer: 19°C versus 14°C in Paris, a difference of 5°C.
```

What differs is how you write it and how you test it:

| Example | Lines in `main.py` | Offline test double | Tests |
| --- | --- | --- | --- |
| [`11-langgraph`](../../examples/11-langgraph/README.md) | ~200 | `GenericFakeChatModel` subclass | 6 |
| [`11-crewai`](../../examples/11-crewai/README.md) | ~170 | your own `BaseLLM` subclass | 6 |
| [`11-autogen`](../../examples/11-autogen/README.md) | ~150 | `ReplayChatCompletionClient` | 4 |
| [`11-agent-framework`](../../examples/11-agent-framework/README.md) | ~170 | your own `BaseChatClient` + `FunctionInvocationLayer` | 5 |
| [`11-openai-agents-sdk`](../../examples/11-openai-agents-sdk/README.md) | ~170 | `agents.testing.ScriptedModel` | 6 |
| [`11-claude-agent-sdk`](../../examples/11-claude-agent-sdk/README.md) | ~160 | none: needs the Claude Code runtime and a key | 5 + 1 live |
| [`11-llamaindex`](../../examples/11-llamaindex/README.md) | ~140 | `MockFunctionCallingLLM` | 4 |
| [`11-pydantic-ai`](../../examples/11-pydantic-ai/README.md) | ~150 | `FunctionModel`, `TestModel` | 5 |

The line counts include the same two tools, comments and a trace printer, so they are close. The real difference is in the concepts you have to learn, shown on each page.

## 💻 Code

The quickest way to feel the difference is to see one tool defined in several frameworks. The function body is identical; only the wrapping changes.

```python
# Plain Python + provider SDK (11.9): you write the schema yourself.
WEATHER_SPEC = {
    "name": "get_weather",
    "description": "Get the current temperature in °C for one city.",
    "input_schema": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]},
}

# OpenAI Agents SDK (11.5) and LangGraph (11.2): a decorator reads the type hints and docstring.
from agents.decorators import tool          # LangGraph: from langchain.tools import tool

@tool
def get_weather(city: str) -> str:
    """Get the current temperature in °C for one city.

    Args:
        city: City name, e.g. 'Paris'.
    """
    ...

# Pydantic AI (11.8): the decorator also registers the tool on one agent.
@agent.tool_plain
def get_weather(city: str) -> str: ...

# Microsoft Agent Framework (11.4) and LlamaIndex (11.7): pass the plain function.
agent = Agent(client=client, instructions=INSTRUCTIONS, tools=[get_weather, calculator])

# Claude Agent SDK (11.6): an async handler that returns MCP content blocks.
@tool("get_weather", "Get the current temperature in °C for one city.", {"city": str})
async def get_weather(args: dict) -> dict:
    return {"content": [{"type": "text", "text": "..."}]}
```

Full, runnable versions with tests: [`examples/11-*`](../../examples/README.md), one folder per framework, each with its own `requirements.txt`.

## 🚨 Common mistakes & gotchas

- **Choosing by popularity.** Stars measure attention, not fit. Start from your requirements (see [11.10](./11.10-how-to-choose.md)).
- **Trusting old tutorials.** These libraries change fast: AutoGen is archived, LangChain moved its agent helpers, Pydantic AI is on major version 2. Check the version a tutorial used, and pin your own versions.
- **Assuming "model-agnostic" means "no differences".** Features such as structured output, hosted tools and parallel tool calls differ by provider, even inside one framework. Test with the model you will ship.
- **Installing every framework into one environment.** They pin many packages and can conflict. Give each its own [virtual environment](../../GLOSSARY.md#virtual-environment).
- **Forgetting the telemetry defaults.** Some frameworks send traces or anonymous usage data by default (OpenAI Agents SDK tracing, CrewAI telemetry). Read the docs and switch it off where you must.

## ✅ Key takeaways

- Every framework packages the same five parts; learn to spot them and any framework gets easier.
- The real choice is how much control you hand over: your own loop, an agent SDK, an orchestration framework, or a full harness.
- Most frameworks ship a fake model for offline tests. Use it from day one.
- AutoGen is archived; Microsoft points new users to Microsoft Agent Framework.
- Pin versions and re-check the docs: this landscape moves every month.
