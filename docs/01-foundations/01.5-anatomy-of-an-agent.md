# 1.5 Anatomy of an agent

> **Difficulty:** 🟢 Beginner · **Reading time:** ~10 min · **Prerequisites:** [1.1 What is an AI agent?](./01.1-what-is-an-ai-agent.md), [1.4 How LLMs work](./01.4-how-llms-work.md)

**In one sentence:** Every agent is built from five parts (a model, instructions, tools, memory and a loop), and knowing them tells you where to look when something goes wrong.

## 🤔 Why does this matter?

Agent frameworks use a lot of different names: crews, graphs, runners, handoffs, toolkits. Underneath, they all assemble the same five parts. Once you can see those parts, three things get easier:

- **Learning a framework.** You ask "where do the tools go? where is the loop?" instead of memorising new vocabulary.
- **Debugging.** A wrong answer is usually a problem with one part: a vague instruction, a badly described tool, missing memory, or a loop that stopped too early.
- **Designing.** You can decide each part on purpose instead of accepting defaults.

## 🧠 The idea, in plain words

Back to the new intern from [1.1](./01.1-what-is-an-ai-agent.md):

| Part | The intern | The agent |
| --- | --- | --- |
| ① **Model** | Their brain: reading, reasoning, deciding | The LLM |
| ② **Instructions** | The briefing on day one: role, goals, rules | The system prompt |
| ③ **Tools** | Logins to the systems they may use | Functions the model can ask you to run |
| ④ **Memory** | Their notebook (today's work) and the company wiki (what's known) | The conversation so far, plus stored facts and documents |
| ⑤ **Loop** | The habit of "try, check, try again" until the job is done | Code that repeats think → act → observe, with limits |

The first four parts are what the agent *has*. The loop is what it *does*. Without the loop you have a model with some extras; with it, you have an agent.

## 🔍 How it works, step by step

**① Model.** The [LLM](../../GLOSSARY.md#large-language-model-llm) that reads the context and decides the next step. Choosing a model is a trade between capability, speed and cost. Many production systems use more than one: a capable model for hard decisions and a smaller one for simple steps ([16.3](../16-cost-and-performance/16.3-model-routing.md)).

**② [Instructions](../../GLOSSARY.md#instructions).** Usually the [system prompt](../../GLOSSARY.md#system-prompt). Good instructions state the agent's role, its goal, the rules it must follow, how to use its tools, and when to stop or ask for help. Vague instructions are the most common cause of strange agent behaviour.

**③ Tools.** Each [tool](../../GLOSSARY.md#tool) is a normal function plus a description the model reads: a name, what it does, and a JSON Schema for its inputs. The model sees only the description, never your code, so the description is part of the interface. Chapter 03 is all about tools.

**④ Memory.** Two kinds:

- *[Short-term](../../GLOSSARY.md#short-term-memory):* the conversation in the current run, including every tool call and result. It lives in the context window ([1.4](./01.4-how-llms-work.md)).
- *[Long-term](../../GLOSSARY.md#long-term-memory):* anything kept between runs, such as user preferences, past outcomes or documents. Your code stores it and puts the relevant parts back into the context when needed. Chapters 05 and 06 cover this.

**⑤ Loop.** The [agent loop](../../GLOSSARY.md#agent-loop): the control code that calls the model, runs the requested tools, adds the results to memory and repeats. It also enforces limits (steps, time, cost) and handles errors. Chapter 02 builds it properly.

## 💡 Worked example

From [`examples/01-anatomy-of-an-agent`](../../examples/01-anatomy-of-an-agent/README.md), a travel assistant with two tools, asked *"Is it warmer in Paris or Rome right now, and by how much?"*

```text
step 1: get_weather({'city': 'Paris'}) -> {"city": "Paris", "temp_c": 14}
step 1: get_weather({'city': 'Rome'}) -> {"city": "Rome", "temp_c": 19}
step 2: calculator({'expression': '19 - 14'}) -> 5
step 3: answer

Answer: Rome is warmer: 19°C versus 14°C in Paris, a difference of 5°C.
```

Mapping the run to the five parts:

| What happened | Part |
| --- | --- |
| The system prompt said *"use get_weather for real temperatures, never guess"* and *"use calculator for arithmetic"* | ② Instructions |
| In step 1 the model asked for **both** cities at once, as two tool calls | ① Model, ③ Tools |
| The temperatures came back and were added to the conversation | ④ Short-term memory |
| *"Prefers temperatures in Celsius"* was injected from stored facts | ④ Long-term memory |
| The model saw both results, then chose the calculator, then chose to stop | ⑤ Loop |

## 💻 Code

The `Agent` class from the example, slightly simplified, with each part labelled:

```python
@dataclass
class Agent:
    model: LLM                                         # ① MODEL
    instructions: str                                  # ② INSTRUCTIONS (system prompt)
    tools: dict[str, tuple[Callable[..., str], ToolSpec]]  # ③ TOOLS: function + description
    facts: list[str] = field(default_factory=list)     # ④ MEMORY (long-term)
    max_steps: int = 6                                 # ⑤ LOOP limit

    def run(self, goal: str) -> str:
        messages = [user(goal)]                        # ④ MEMORY (short-term)
        system = self.instructions + "".join(f"\n- {f}" for f in self.facts)
        specs = [spec for _, spec in self.tools.values()]

        for _ in range(self.max_steps):                # ⑤ LOOP
            reply = self.model.chat(messages, system=system, tools=specs)  # ① think
            messages.append(reply.to_message())
            if not reply.tool_calls:
                return reply.text                      # the model chose to stop
            for call in reply.tool_calls:              # ③ act
                fn, _ = self.tools[call.name]
                messages.append(tool_result(call.id, fn(**call.arguments)))  # ④ observe
        return "I could not finish within the step limit."
```

A tool is a plain function plus its description:

```python
WEATHER_SPEC = {
    "name": "get_weather",
    "description": "Get the current temperature in °C for one city.",
    "input_schema": {
        "type": "object",
        "properties": {"city": {"type": "string", "description": "City name, e.g. 'Paris'."}},
        "required": ["city"],
    },
}
```

Full, runnable version with tests: [`examples/01-anatomy-of-an-agent/main.py`](../../examples/01-anatomy-of-an-agent/main.py). Every framework in [chapter 11](../11-frameworks/README.md) has a place for each of these five parts.

## 🚨 Common mistakes & gotchas

- **Blaming the model first.** Most failures come from the other four parts: unclear instructions, a misleading tool description, missing context, or no step limit. Check those before switching models.
- **Tool descriptions written for humans, not the model.** The model only knows what the description says. "Gets data" is useless; "Get the current temperature in °C for one city" is clear. See [3.4](../03-tools-and-function-calling/03.4-designing-good-tools.md).
- **Too many tools.** Each tool description takes up context and gives the model another way to choose wrongly. Start with the few you need.
- **Treating memory as "store everything".** More context isn't always better: irrelevant history distracts the model and costs money. Decide what to keep ([5.5](../05-memory/05.5-memory-design-trade-offs.md)).
- **A loop with no limits or error handling.** One failing tool or one confused model can loop forever. See [2.4](../02-the-agent-loop/02.4-stopping-conditions.md) and [2.5](../02-the-agent-loop/02.5-handling-errors-in-the-loop.md).

## ✅ Key takeaways

- Five parts: ① model, ② instructions, ③ tools, ④ memory, ⑤ loop.
- The first four are what the agent has; the loop is what makes it an agent.
- The model only sees tool *descriptions*, so they are part of your interface.
- Memory is short-term (this run's conversation) and long-term (stored between runs).
- When debugging, check each part in turn; it's rarely "just the model".
